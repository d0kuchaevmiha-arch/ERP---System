# Резервное копирование

На локальном Compose: `docker compose exec -T db pg_dump -U postgres -Fc app_db > backup.dump`. Проверка восстановления **только на отдельной тестовой базе**: `createdb test_restore` и `pg_restore --no-owner --dbname=test_restore backup.dump` при доступном PostgreSQL.

**Перед обновлением на версию с миграциями (0.2.0)** сделайте дамп: миграции применяются автоматически при старте контейнера. Baseline существующей БД данные не меняет, а миграция `0001` только добавляет колонки со значениями по умолчанию и новую таблицу — но копия нужна на случай ручной сверки. Альтернатива для dev-volume — копия тома целиком при остановленных контейнерах:

```bash
docker run --rm -v <проект>_pgdata:/from:ro -v <проект>_pgdata_backup:/to alpine cp -a /from/. /to/
```

**Перед обновлением на 0.3.0** — тоже дамп: миграция `0002` добавляет колонки и заполняет их у существующих строк (`server_received_at`, `updated_at` из `created_at`); значения прежних колонок не меняются (проверено сверкой контрольных сумм на dev-томе).

Новые таблицы в дампе: `change_log` (восстанавливается как есть; записи старше 90 дней удалятся при первом запуске), `sync_ops` (ключи повторов — нужны после восстановления, чтобы повтор старого запроса не создал дубль), `task_progress_log`, `org_counters` (после восстановления нумерация заявок продолжится с сохранённого значения).

Журнал `drizzle.__drizzle_migrations` входит в дамп; после восстановления повторный запуск миграций — no-op.

Для production: зашифрованные копии вне узла, расписание (cron/systemd timer), retention и регулярная проверка восстановления. Автоматическая задача backup пока не поставляется (P5).

## Данные десктопа (0.4.0)
Ноутбук хранит **копию** данных сервера (реплику) — источник истины остаётся на сервере, отдельное резервное копирование реплики не требуется: при потере её можно загрузить заново (подключить устройство). Перед обновлением структуры локальной базы приложение само делает «холодную» копию `%APPDATA%\ERP-Energotech\pgdata` в `backups\` (хранятся 5 последних). **С 0.5.0 на ноутбуке есть очередь (`outbox`) — то, что введено без связи и ещё не принято сервером.** Пока операция не отправлена, её единственная копия — на ноутбуке.
- Очередь входит в `pgdata` и в «холодные» копии `backups\pgdata-*` перед обновлением структуры базы.
- **Экспорт очереди в файл** (меню «Файл», экраны очереди, экран входа отозванного устройства) — JSON с введёнными данными и их состоянием, без токена и паролей. Используйте его перед переустановкой Windows, заменой ноутбука, при отзыве устройства.
- Не удаляйте `%APPDATA%\ERP-Energotech` при непустой очереди: индикатор «Офлайн · N изменений в очереди» должен показать 0 или файл экспорта должен быть сохранён.
- Отдельного автоматического резервного копирования очереди нет (Допущение): риск — выход из строя диска ноутбука до появления связи.

**Сервер (0.5.0):** в дампе появились `sync_conflicts` (открытые конфликты «Требует решения» нужно восстановить вместе с `sync_ops`, иначе повтор операции с ноутбука будет принят заново как новая) и поля `users.blocked_at` / `unblocked_at`.
