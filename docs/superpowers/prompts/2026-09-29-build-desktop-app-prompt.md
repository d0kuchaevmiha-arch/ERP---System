```markdown
## Цель продукта (кратко)
Одна организация (>100 пользователей) работает с центральным сервером (за VPN/прокси).
Десктоп-приложение для Windows 10/11 (ERP-Энерготех-Setup.exe → ярлык → окно) держит
локальную реплику «своих» объектов во встроенном PostgreSQL и позволяет полноценно вводить
данные офлайн; при появлении связи операции отправляются на сервер как команды (outbox),
сервер применяет их через те же бизнес-правила, спорное попадает в «Требует решения».
Онлайн-пользователи видят изменения друг друга ≤ 5 с (LISTEN/NOTIFY → SSE → pull).
Браузер работает с сервером онлайн. docker compose для разработки продолжает работать.

## Жёсткие правила
- Не ломай работающие сценарии и docker compose up. Схему меняй только версионными
  миграциями Drizzle (drizzle-kit generate + migrator); drizzle-kit push не использовать.
  Для существующих БД — baseline без изменения данных.
- Вся запись идёт через доменный слой (src/server/domain/commands): Zod-валидация на сервере,
  authorize (роль + project_access ВСЕГДА), транзакция, audit, change_log.
- Деньги — NUMERIC и строки/BigInt, никаких float как источника истины.
  План, факт и прогноз не смешивать; у каждого факта — происхождение
  (origin, device_id, device_created_at, server_received_at).
- Данные никогда не теряются молча: отклонённые и спорные операции видны пользователю
  с причиной.
- Безопасность: секреты не в коде, не в образе и не в установщике (.env исключён белым
  списком); на клиенте Postgres и Next слушают только 127.0.0.1; Electron —
  contextIsolation, sandbox, без nodeIntegration, внешние ссылки в системном браузере,
  проверку TLS не отключать.
- Не выдумывай требования, нормативы, интеграции, тарифы. Всё неподтверждённое помечай
  «Допущение» (список допущений — раздел 14 спецификации).
- Отвечай по-русски, кратко. Для существенных решений — альтернативы и рекомендация.
- Сложные термины поясняй простым примером из жизни.
- Если не можешь что-то проверить в своей среде (например, Windows-установщик, SmartScreen,
  антивирус) — прямо скажи и дай мне чек-лист ручной проверки.
```

## Промпты подпроектов (отправлять после «ок» по предыдущему)

### P2 — доменный слой и обновление в реальном времени
```markdown
P1 принят. Переходи к P2 по спецификации (разделы 5, 6.5, 12):
вынести запись из route.ts в src/server/domain/commands с единым реестром;
идемпотентность (Idempotency-Key / op_id, таблица sync_ops); version + 409;
task_progress_log; change_log в той же транзакции; pg_notify после commit;
SSE /api/sync/events с фильтром по доступу; в браузерном UI — авто-обновление с debounce
1–2 с и резервный опрос 30 с. Критерий: изменение одного пользователя видно другому ≤ 5 с,
повтор команды не дублирует данные. Сначала план, жди «ок».
```

### P3 — десктоп-клиент с локальной репликой (онлайн)
```markdown
P2 принят. Переходи к P3 (разделы 3, 4.3, 6.1–6.3, 8, 10, 12):
Next standalone (DESKTOP_BUILD=1), ERP_MODE=client; Electron main (single instance,

embedded-postgres 16 в %APPDATA%\ERP-Energotech, секреты через safeStorage, бэкап pgdata
перед миграцией; экран «адрес сервера + вход», регистрация устройства; snapshot + pull
с индикатором прогресса; sync-agent отдельным процессом; scripts/estimate-replica.ts;
electron-builder NSIS одной командой npm run dist. Критерии приёмки — раздел 12, P3.
Если собрать/проверить .exe в своей среде нельзя — дай мне пошаговый чек-лист проверки

```

### P4 — офлайн-ввод и синхронизация
