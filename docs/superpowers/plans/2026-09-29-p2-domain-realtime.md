# P2 — Доменный слой + реальное время: план реализации

- **Спецификация:** §4.1, §4.2 (`change_log`, `sync_ops`, `audit_logs` + происхождение), §5, §5.1, §6.5, §11, §12 (P2); граница P1/P2 — вариант A.
- **Статус:** согласован («ок» 2026-09-29, по созданию объекта — вариант A), выполнен — см. CHANGELOG 0.3.0.
- **Критерии приёмки P2 (§12):** изменение одного пользователя видно другому ≤ 5 с; повтор команды с тем же ключом не дублирует. Плюс всегда: typecheck / lint / build / тесты / smoke.

## 0. Отправная точка (после P1, проверено)
- Каркас `src/server/domain/commands` и `runCommand` есть; 20 команд; вся запись через них.
- Нет: происхождения фактов, `version`/`updated_at`, `task_progress_log`, `change_log`, идемпотентности, NOTIFY/SSE; браузер обновляет данные только после своего действия.
- Номер заявки — `ЗК-<Date.now base36>` (возможны коллизии, не «сквозной»).
- Открыт вопрос из P1: создатель объекта без `project_access` его не видит (см. «Вопрос» в конце).

## 1. Решения (рекомендуемые; альтернативы — в скобках)
1. **Контекст команды** расширяется полями происхождения: `origin` ('online' | 'offline'), `deviceId`, `deviceCreatedAt`, `opId`, `serverReceivedAt`. Для HTTP: `online`, `deviceCreatedAt = serverReceivedAt = now()`. P4 (sync push) передаст офлайн-значения тем же путём.
2. **Идемпотентность — одна таблица `sync_ops`** и для HTTP (`Idempotency-Key`), и для будущего push (альт.: отдельная таблица для HTTP — дублирование). Запись в `sync_ops` — в той же транзакции, что и данные; отклонённая операция сохраняется со статусом `rejected` отдельной транзакцией, повтор ключа возвращает тот же результат. Тот же ключ с другой командой/данными → 422.
3. **`change_log`** пишется хелпером `recordChange(tx, …)` из каждой команды; `pg_notify('erp_changes', {org, projectIds, maxSeq})` — в той же транзакции (доставляется только после commit). В payload только номера — никаких данных.
4. **Сигналы:** в каждом экземпляре приложения один «хаб» (одно выделенное `LISTEN`-соединение, переподключение с паузой) раздаёт события подписчикам SSE. Фильтр: своя организация и объекты пользователя (`project_id is null` — всей организации). `GET /api/sync/events` — cookie (device token — P3), heartbeat 25 с, сессия перепроверяется на каждом heartbeat (блокировка → поток закрывается).
5. **Браузер:** `EventSource` → debounce 1,5 с → `refresh()`; при обрыве SSE — опрос раз в 30 с. Кнопки POST отправляют `Idempotency-Key` (защита от двойного клика и повтора при сбое сети).
6. **`version`/`updated_at`** на 9 таблицах §4.1; каждое UPDATE в командах увеличивает `version`. Команды, изменяющие существующую запись (`approvals.decide`, `purchases.receive`, `users.update`), принимают необязательный `version`; несовпадение → 409 «Запись изменил другой пользователь — обновите данные». (`progress.set` по §5.1 не конфликтует — решает время факта.)
7. **`progress.set`:** каждый факт → `task_progress_log`; в `tasks` применяется, только если `device_created_at` ≥ времени текущего значения (`tasks.progress_reported_at`), иначе остаётся в истории.
8. **Номер заявки** — серверный сквозной номер организации из счётчика `org_counters` (UPSERT … RETURNING, без гонок); `purchases.local_ref` — для офлайн-номера (P4). Старые номера не меняются.
9. **Хранение `change_log` 90 дней** (допущение §14): очистка хабом при старте и раз в сутки.

## 2. Шаги (после каждого: typecheck, lint, build, тесты, коммит)

### Шаг 1. Миграция 0002 (только добавления)
- Факты (`expenses`, `stock_movements`, `purchases`): `origin text not null default 'online'`, `device_id uuid`, `device_created_at timestamptz`, `server_received_at timestamptz not null default now()`, `op_id uuid`. Бэкфилл существующих: `server_received_at = created_at`, `device_created_at` = NULL (неизвестно).
- `audit_logs`: `origin`, `device_id`, `device_created_at`.
- `version int not null default 1`, `updated_at timestamptz not null default now()` на projects, tasks, purchases, approvals, materials, warehouses, counterparties, contracts, budget_lines.
- Новые таблицы: `task_progress_log`, `change_log` (seq bigserial, индекс (organization_id, seq)), `sync_ops`, `org_counters`; `tasks.progress_reported_at`, `purchases.local_ref`.
- Тесты: миграция на пустой БД и на БД «после push» с данными (бэкфилл корректен, строки не теряются).

### Шаг 2. Происхождение фактов и аудита
- Тесты (красные): расход/движение/заявка, созданные по HTTP, имеют `origin='online'`, `server_received_at`, `device_created_at`, `op_id`; аудит тоже.
- Контекст команды + заполнение полей во всех командах, создающих факты.

### Шаг 3. `change_log` + NOTIFY
- Тесты: каждая команда пишет строки `change_log` с правильными `organization_id`/`project_id`/`entity`; при ошибке (откат) строк нет; уведомление приходит только после commit и содержит `maxSeq`, но не данные.
- `recordChange` во всех 20 командах (в т. ч. `user`, `project_access` — для пересчёта видимости).

### Шаг 4. Идемпотентность
- Тесты: повтор с тем же ключом → один набор строк и тот же ответ; два одновременных запроса с одним ключом → одна запись; тот же ключ с другими данными → 422; повтор отклонённой операции → та же ошибка; ключ одного пользователя недоступен другому.
- `sync_ops`, `runCommand(…, { opId })`, заголовок `Idempotency-Key` (UUID) во всех POST/PATCH/PUT/DELETE; UI отправляет ключ.

### Шаг 5. `version` / 409
- Тесты: устаревший `version` в согласовании / приёмке / изменении пользователя → 409, данные не изменены; без `version` — как раньше; каждое изменение увеличивает `version` и `updated_at`.

### Шаг 6. `task_progress_log`
- Тесты: каждый факт в истории с автором и временем; более ранний по `device_created_at` факт не перезаписывает `tasks.progress`, но виден в истории; `actualQuantity: 0` по-прежнему сохраняется.

### Шаг 7. Номер заявки
- Тесты: 20 параллельных `purchases.create` → 20 разных последовательных номеров; организации нумеруются независимо; старые номера не трогаются.

### Шаг 8. Хаб изменений + SSE
- Тесты на настоящем PG: подписчик своей организации получает событие < 1 с после commit; чужая организация и объект без доступа — не получают; выдача доступа начинает доставку; откат — ничего; обрыв LISTEN-соединения → переподключение.
- `src/server/realtime/hub.ts`, `GET /api/sync/events` (SSE, heartbeat 25 с, закрытие при отзыве сессии), очистка `change_log` > 90 дней.

### Шаг 9. Автообновление в браузере
- `EventSource` + debounce 1,5 с + опрос 30 с при обрыве; индикатор «обновлено ЧЧ:ММ» в шапке.
- Проверка вручную: два окна (директор и РП), изменение в одном видно в другом без перезагрузки.

### Шаг 10. Приёмка P2
- `scripts/smoke.ts`: + подписка SSE вторым пользователем → действие первого → событие ≤ 5 с (замер в выводе); + повтор с `Idempotency-Key` не создаёт дубль.
- `docker compose up --build` на существующем volume (миграция 0002 с бэкфиллом, данные целы — сверка контрольных сумм, как в P1) и на новом.
- Документы: api.md (Idempotency-Key, version/409, SSE), database.md (0002), permissions.md, deployment.md (прокси без буферизации SSE — замечание для P5), backup.md, CHANGELOG 0.3.0; допущения — в §14.

## 3. Допущения P2 (внести в §14 после «ок»)
| Вопрос | Допущение |
|---|---|
| Формат номера заявки | `ЗК-<год>-<NNNNN>`, сквозной счётчик организации (не сбрасывается по годам) |
| Идемпотентность | ключ — UUID; хранение `sync_ops` бессрочно до P5 (очистка — вместе с политикой бэкапов) |
| Факты до 0.3.0 | `origin='online'`, `server_received_at = created_at`, `device_created_at` неизвестно (NULL) |
| Задержка обновления в браузере | ≤ 5 с при живом SSE (debounce 1,5 с); без SSE — до 30 с |

## 4. Риски
- SSE через прокси с буферизацией не доставляет события — в dev прокси нет, в P5 настраивается (`X-Accel-Buffering: no` уже выставляется).
- Next route handler держит соединение SSE открытым; 100 одновременных подписчиков на экземпляр — ожидаемо нормально, нагрузочно не проверяется в P2.
- Полная перезагрузка сводки (`refresh`) на каждое событие при большом числе объектов тяжела — частично гасит debounce; лёгкие эндпоинты — по мере роста (§9).
