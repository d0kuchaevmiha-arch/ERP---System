# Доступ

## Сессии и вход
- Сессия — подписанная HMAC HTTP-only cookie (SameSite=Lax, Secure в production), срок 7 дней. Формат `userId.sessionVersion.expires.hmac`.
- `SESSION_SECRET` обязателен и не короче 32 символов; запасных значений нет — без него сервер не выдаёт и не принимает сессии.
- Каждый запрос проверяет пользователя в БД: `is_active = false` или изменившийся `session_version` — сессия недействительна сразу. `session_version` растёт при блокировке, сбросе и смене пароля.
- Пароль — scrypt с индивидуальной солью, не короче 10 символов (Допущение). Временный пароль (16 символов) выдаётся при создании и сбросе; пока он не сменён, доступны только вход и смена пароля.
- Лимит входа: 10 неудач за 15 минут по ключу email+IP, счётчик в таблице `login_attempts` (общий для всех экземпляров). IP клиента берётся из `X-Forwarded-For` **только** при `TRUSTED_PROXY=1` (крайний правый адрес — добавленный вашим прокси); без этого ключ фактически по email.
- Для несуществующего email тоже считается scrypt, чтобы по времени ответа нельзя было проверять адреса.
- Изменяющие запросы с чужим `Origin` отклоняются.

## Роли
`super_admin`, `director`, `project_manager`, `construction_manager`, `foreman`, `procurement_manager`, `warehouse_manager`, `finance_manager`, `accountant`, `read_only`.

| Правило | Кто |
|---|---|
| Все объекты своей организации без `project_access` | director, super_admin |
| Остальные — только объекты из `project_access` | `view` — просмотр, `edit` — ввод данных |
| Запись | все роли, кроме `read_only`, и только в объекты с `edit` (для director/super_admin — любые объекты организации) |
| Согласование заявки, приёмка | director, super_admin, project_manager, procurement_manager + `edit` на объект заявки |
| Управление пользователями и доступами | director, super_admin своей организации (Допущение); `super_admin` назначает и изменяет только `super_admin`; себя заблокировать или сменить себе роль нельзя |
| Смена своего пароля | все роли, включая `read_only` |
| Создание объекта | роли записи; автор, которому не видны все объекты организации, автоматически получает `edit` на созданный объект (решение P2) |
| Сигналы реального времени (SSE) | только своя организация и объекты из доступа; изменения уровня организации — всем её пользователям (без данных); поток закрывается при блокировке, сбросе и смене пароля |
| Повтор по `Idempotency-Key` | ключ привязан к пользователю: чужой ключ не возвращает чужой результат (422) |

## Где проверяется
Вся запись идёт через доменные команды `src/server/domain/commands/*`: роль → Zod → `authorize` (организация + `project_access`, **всегда**, в том числе когда объект выводится из работы, заявки или склада) → транзакция → аудит. Ссылки на сущности другой организации — 404, на работу/склад/договор другого объекта той же организации — 422.

Чтение — `src/server/read/overview.ts`: только своя организация и доступные объекты. Справочники (материалы, контрагенты, склады) — вся организация; остатки считаются по всем складам организации; договоры без объекта — director, super_admin, finance_manager, accountant; уведомления — только свои; журнал аудита — director/super_admin вся организация, остальные — свои действия (Допущения).

`src/lib/permissions.ts` — клиентское зеркало для скрытия недоступных кнопок; настоящая проверка — только на сервере.

## Ограничения
Гранулярные права сверх ролей, ACL по подразделениям и делегирование не реализованы. Несколько независимых организаций на одном сервере — не цель этой итерации. Для доступа из интернета нужен внешний rate-limit на прокси.
