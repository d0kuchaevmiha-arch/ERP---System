# Changelog

## 0.5.1 — исправление

- **Десктоп: новый объект не появлялся на ноутбуке.** Если на экране «Доступно офлайн» хоть раз нажали «Сохранить», набор становился явным списком, и объекты, созданные позже (в том числе самим пользователем), на ноутбук не загружались; повторное создание давало «запись уже существует». Теперь объект, созданный в десктопе, сразу добавляется в набор и загружается; «Сохранить» со всеми отмеченными объектами сохраняет набор по умолчанию (новые объекты приезжают сами).
- Повторный код объекта — понятный отказ «Объект с кодом «…» уже есть: ‹название›».

## 0.5.0 — P4: офлайн-ввод

**При обновлении сервера:** сделайте дамп (`docs/backup.md`); миграция `0004` применяется автоматически и не меняет существующие данные. Десктоп: после обновления программа при каждом запуске спрашивает пароль.

- **Ввод без связи в десктопе**: выполнение работ, расходы, заявки (временный номер `ЛОК-…`), приход, возврат, выдача, списание, приёмка.
  - Данные проверяются теми же правилами, что на сервере (роль, доступ к объекту, поля, остаток с учётом очереди), и сохраняются в очереди на ноутбуке с пометкой «не синхронизировано».
  - При связи очередь уходит на сервер по порядку ввода. Сервер проводит каждую операцию обычной командой с происхождением «офлайн» (устройство, время ввода, время приёма).
- **Отклонённое не теряется**: изменения на ноутбуке откатываются, операция с причиной видна в «Не принято сервером». Причины: нет доступа, отклонена связанная операция, введено во время блокировки пользователя и т. д.
- **Спорное — людям**: если на сервере не хватило остатка или приняли больше заказа, операция попадает в «Требует решения» (браузер и десктоп).
  - Кладовщик/РП (для приёмки — РП/снабженец, всегда — директор) может «провести с исправлением» через обычные проверки или «отклонить» с причиной; решение пишется в аудит.
  - Автор видит итог на ноутбуке.
- **Только онлайн**: согласование, объекты, работы, бюджеты, договоры, справочники, пользователи; без связи — «Нужна связь с сервером».
- **Офлайн-вход**: пароль при запуске.
  - Без связи — по сохранённой scrypt-проверке (DPAPI) не дольше 7 дней; часы назад окно не продлевают; после 5 ошибок — пауза.
  - Отзыв устройства или блокировка прекращают офлайн-вход.
- **Индикатор**: «Онлайн · синхронизировано 12:04», «Офлайн · 7 изменений в очереди», «Есть отклонённые (2)», «Требует решения (1)».
- **Экспорт очереди в файл**: меню «Файл», экраны очереди, экран входа отозванного устройства.
- **API**: `POST /api/sync/push`, `POST /api/auth/device/verify`, `/api/v1/conflict-resolve`, `/api/v1/conflict-discard`; в офлайн-командах необязательный `id` строки; ошибка остатка — код `insufficient_stock`, превышение заказа — `over_receipt`, повтор уникального значения — `duplicate`.
- **Проверено**:
  - 12 сценарных sync-тестов (§11) на двух эмулированных клиентах и PostgreSQL 16;
  - E2E собранного приложения: ввод без связи, запуск без связи, связь вернулась — всё на сервере; повторный запуск 4,0 с без учёта ввода пароля;
  - smoke против docker compose.

## 0.4.0 — P3: десктоп-клиент с репликой (онлайн)

- **Десктоп для Windows** (`ERP-Энерготех-Setup.exe`, Electron 44, NSIS, установка в профиль): встроенный PostgreSQL 16 на `127.0.0.1`, тот же интерфейс в режиме `ERP_MODE=client`, чтение из локальной реплики, запись — онлайн через сервер (ответ после того, как реплика догнала изменение). Подробности и чек-лист — `docs/desktop.md`.
- **Устройства**: регистрация по email+паролю, токен (на сервере — SHA-256, на ноутбуке — DPAPI), отзыв владельцем/администратором, автоматически — при блокировке и сбросе пароля; список устройств на экране «Пользователи».
- **Синхронизация**: `/api/sync/scope | snapshot | pull` (протокол v1, `X-Sync-Protocol`, 426/410), офлайн-набор объектов («Доступно офлайн»), удаление данных объекта с ноутбука при отзыве доступа, сигналы SSE для устройства, `X-Change-Seq` в ответах команд.
- **Оценка объёма реплики**: `scripts/estimate-replica.ts`.
- Исправления, найденные при работе над десктопом: проверка `Origin` теперь сравнивает с `Host`/`X-Forwarded-Host` (за прокси и в standalone записи из браузера получали бы 403); интерфейс перечитывает данные после подключения SSE (изменение во время загрузки страницы не терялось бы); Docker-образ не тянет десктопные зависимости.
- Проверено на этой машине: E2E собранной программы (первый запуск, изменения в обе стороны, повторный запуск 3,7 с, порт 3000 занят, второй экземпляр, нет процессов после закрытия) и установщика (установка, удаление с сохранением данных, переустановка, повторный запуск 4,6 с).

## 0.3.0 — P2: доменный слой + реальное время

**При обновлении:** сделайте дамп (`docs/backup.md`); миграция `0002` применяется автоматически и не меняет существующие значения.

- Реальное время: изменения одного пользователя видны другим без перезагрузки (LISTEN/NOTIFY → SSE `/api/sync/events` → обновление сводки через 1,5 с; без SSE — опрос раз в 30 с). Индикатор «Онлайн · обновлено ЧЧ:ММ» в шапке. Замер smoke: сигнал второму пользователю за десятки миллисекунд.
- `change_log` пишется в той же транзакции, что и данные; сигнал уходит только после commit и не содержит данных; хранение 90 дней.
- Идемпотентность: `Idempotency-Key` на всех изменяющих запросах (результат в `sync_ops`); интерфейс отправляет ключ на каждое действие.
- `version`/`updated_at` на изменяемых таблицах; устаревшая версия при согласовании/приёмке → 409.
- История прогресса `task_progress_log`: более ранний по времени устройства факт не перезаписывает текущий.
- Происхождение фактов и аудита: `origin`, `device_id`, `device_created_at`, `server_received_at`, `op_id` (готово для офлайн-синхронизации P4).
- Номер заявки — сквозной серверный `ЗК-<год>-<NNNNN>`; временный номер клиента — `localRef`.
- Автор объекта (не директор) автоматически получает `edit`-доступ к нему.
- Надёжность: обрыв простаивающего соединения с БД больше не роняет процесс.

## 0.2.0 — P1: безопасный многопользовательский сервер

**Внимание при обновлении:** сделайте дамп БД (`docs/backup.md`); после обновления все пользователи входят заново (новый формат сессии); `SESSION_SECRET` обязателен (≥ 32 символов).

- Версионные миграции Drizzle (`drizzle/`, `npm run db:migrate`); `drizzle-kit push` больше не используется. Существующая БД, созданная через `push`, сверяется со схемой и помечается baseline без изменения данных.
- Без входа данные не отдаются (страницы → `/login`, API → 401). Флаг `ERP_PRIVATE_MODE` удалён.
- Чтение только в пределах организации и доступных объектов (`project_access`); уведомления — свои; аудит — по роли.
- Вся запись — через доменные команды `src/server/domain/commands`: роль + `project_access` проверяются всегда, в том числе для прогресса, согласования, приёмки и движений; ссылки на чужие сущности отклоняются.
- Гонки: согласование — условный UPDATE (второе решение — 409 «уже решена ‹кем›»), приёмка — `FOR UPDATE` и суммы в NUMERIC, прогресс — блокировка строки; `actualQuantity = 0` сохраняется.
- Сессии: `session_version` (мгновенный отзыв), блокировка пользователя, секрет без фолбэков. Лимит входа — в БД (`login_attempts`), IP — только от доверенного прокси (`TRUSTED_PROXY=1`).
- Управление пользователями (director/super_admin): создание с временным паролем, роли, блокировка, сброс пароля, доступ к объектам; обязательная смена временного пароля.
- Тесты: Vitest + PostgreSQL 16 (`npm run test:db:up && npm test`) — миграции, сессии, вход, изоляция чтения и записи, гонки, пользователи.
