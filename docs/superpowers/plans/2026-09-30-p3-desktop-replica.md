# P3 — Десктоп-клиент с репликой (онлайн): план реализации

- **Спецификация:** §3 (компоненты, режимы), §4.2 (`devices`), §4.3 (`sync_state`), §6.1–6.3, §6.5, §7, §8, §10, §12 (P3), §13.
- **Статус:** согласован («ок» 2026-09-30), выполнен — см. CHANGELOG 0.4.0 и отчёт.
- **Критерии приёмки P3 (§12):** установка на чистую Windows; повторный запуск < 15 с; порт 3000 занят — работает; второй запуск фокусирует окно; после закрытия нет node/postgres; данные переживают переустановку. Плюс всегда: typecheck / lint / build / тесты / smoke.

## 0. Отправная точка (после P2, проверено)
- Сервер: доменные команды с идемпотентностью, `change_log` + NOTIFY, SSE `/api/sync/events` (только cookie).
- Нет: `devices`, токена устройства, `snapshot`/`pull`, режима `ERP_MODE=client`, Electron-оболочки, установщика.
- Среда: Windows 11 (эта машина), Docker для сервера; чистой Windows-ВМ у меня нет.
- Пакеты (проверено в npm 2026-09-30): `embedded-postgres` / `@embedded-postgres/windows-x64` **16.14.0-beta.17** (MIT; суффикс beta — схема версий пакета, внутри PostgreSQL 16.14), `electron` 44, `electron-builder` 26, `electron-log` 5, `@playwright/test` 1.63.

## 1. Решения (рекомендуемые; альтернативы — в скобках)
1. **Запись в P3 — только онлайн, через сервер.** Локальный Next в режиме client пересылает любую команду на сервер (токен устройства + `Idempotency-Key`) и отвечает, когда реплика догнала изменение (сервер возвращает `X-Change-Seq`, клиент ждёт `last_seq ≥ seq`, до 5 с). Без связи кнопки записи недоступны с пояснением «нужна связь». Outbox и офлайн-запись — P4. (Альт.: сразу локальная запись + outbox — это и есть P4.)
2. **Код десктопа — каталог `desktop/`** в том же репозитории (main-процесс, preload, экраны настройки/загрузки, sync-agent, конфиг electron-builder); Next-приложение и доменный слой общие. Зависимости Electron — devDependencies корня (один `npm ci`).
3. **Локальная БД:** embedded-postgres 16 на `127.0.0.1:<свободный порт>`, `initdb --encoding=UTF8 --locale=C`, пароль генерируется при первом запуске. Схема — те же миграции `drizzle/` + **отдельная папка `drizzle-client/`** для таблиц только клиента (`sync_state`; `outbox`/`local_rows` — P4) со своим журналом — на сервере их нет (§4.3).
4. **Реплика — копия, целостность проверяет сервер:** агент применяет пакеты с `session_replication_role = replica` (без проверки внешних ключей: строки могут прийти не в порядке зависимостей). В реплику не попадают хеши паролей и `audit_logs`.
5. **Токен устройства:** `erpd_<32 байта>`, на сервере — только SHA-256 в `devices.token_hash`; на клиенте — `safeStorage` (DPAPI) в `secrets.bin`. Недействителен при: `revoked_at`, блокировке пользователя, сбросе пароля администратором (сброс отзывает устройства пользователя). Смена своего пароля устройства не отзывает. Регистрация при `must_change_password` → 403 «смените пароль в браузере».
6. **Протокол:** `X-Sync-Protocol: 1` обязателен на `/api/auth/device` и `/api/sync/*`; другой → 426. Pull — строки в текущем состоянии (дедуп по id), `scope` в ответе = объекты, которые реально отдаются; клиент удаляет у себя строки объектов, выпавших из `scope` (так отзыв доступа удаляет объект с ноутбука). Если `since` старше срока хранения `change_log` → 410, клиент делает snapshot заново.
7. **Состав реплики:** своя организация; users (без секретов), свои `project_access`; объекты из офлайн-набора ∩ доступ: projects, tasks, task_dependencies, budget_lines, expenses, purchases, approvals, contracts, task_progress_log; справочники организации: materials, counterparties, warehouses; **движения всех складов организации** (остатки как на сервере, P1-допущение; нужно и для офлайн-предпроверки в P4 — объём проверим скриптом); свои notifications. Офлайн-набор по умолчанию — все доступные объекты, у director/super_admin — пусто (§10); выбор — экран «Доступно офлайн».
8. **Локальный вход в P3:** окно Electron получает одноразовый на запуск cookie-секрет; локальный Next принимает только его (другие программы на `127.0.0.1` данных не получат). Офлайн-вход по scrypt-верификатору — P4.
9. **Адрес сервера:** только `https://`; исключение — `http://localhost`/`127.0.0.1` для разработки и E2E (Допущение). Проверка TLS не отключается.

## 2. Шаги (после каждого: typecheck, lint, build, тесты, коммит)

### Шаг 1. Сервер: устройства и токен
- Миграция `0003`: `devices` (id, user_id, name, app_version, token_hash, registered_at, last_sync_at, revoked_at).
- `POST /api/auth/device` {email, password, deviceName, appVersion} → {deviceId, token, user}; тот же лимит попыток, что и вход. Bearer-токен принимается `/api/v1/*`, `/api/admin/*`, `/api/sync/*` (общая функция «пользователь запроса»: cookie или токен).
- Команда `devices.revoke` (владелец или director/super_admin); сброс пароля и блокировка отзывают устройства; список устройств и «Отозвать» — на экране «Пользователи».
- Тесты: регистрация/отказы, отозванный токен → 401, блокировка → 401, 426 при другой версии протокола, хеш вместо токена в БД, чужая организация.

### Шаг 2. Сервер: offline scope, snapshot, pull
- `src/server/sync/entities.ts` — реестр реплицируемых сущностей (таблица, правило видимости, публичные колонки).
- `GET /api/sync/scope`, `GET /api/sync/snapshot?entity&projects&cursor`, `GET /api/sync/pull?since&limit&projects`; заголовок `X-Change-Seq` в ответах команд.
- Тесты (главные — изоляция): другая организация, объект вне доступа, хеши паролей и аудит никогда не попадают в ответ; дедуп; удаление; `hasMore`; отзыв доступа → объект выпадает из `scope`; 410 после очистки журнала.

### Шаг 3. Клиентская БД и sync-agent (без Electron)
- Миграции `drizzle-client/` (`sync_state`), `src/client/sync/agent.ts`: первый snapshot с прогрессом, pull до `hasMore=false`, upsert с приведением типов, удаление выпавших объектов, локальный NOTIFY после применения; ожидание сигнала SSE сервера или 30 с, при ошибках — пауза до 5 мин (§6.6, без push).
- Тесты на двух настоящих БД (серверная + клиентская): реплика = видимые строки сервера; изменение на сервере доезжает; отзыв доступа удаляет объект; повторный snapshot после 410.

### Шаг 4. Режим `ERP_MODE=client` в Next
- Локальная сессия (cookie-секрет запуска), чтение сводки из реплики тем же `getOverviewFor`.
- Пересылка записи на сервер с ожиданием реплики; `/api/admin/*` и смена пароля — прокси на сервер; без связи — понятная ошибка «нужна связь».
- Локальный SSE по NOTIFY агента → тот же автоповтор сводки в UI; экран «Доступно офлайн».
- Тесты: пересылка (тестовый HTTP-сервер), отказ без cookie-секрета, ожидание `X-Change-Seq`.

### Шаг 5. Electron-оболочка (`desktop/`)
- Main: single-instance (второй запуск фокусирует окно), свободные порты, embedded-postgres (initdb, устаревший `postmaster.pid`, «холодная» копия `pgdata` перед миграцией — хранить 5), миграции, запуск Next standalone и sync-agent через `ELECTRON_RUN_AS_NODE`, экран загрузки (опрос `/api/health`), экран первого запуска «адрес сервера + вход» (preload), `%APPDATA%\ERP-Energotech\{pgdata,backups,logs,config.json,secrets.bin}`.
- Безопасность окна: `contextIsolation`, `sandbox`, без `nodeIntegration`, внешние ссылки — в системном браузере, `will-navigate` на чужие адреса блокируется, TLS не отключается.
- Закрытие окна = выход: агент → Next → `pg_ctl stop -m fast`, при сбое — `taskkill /T /F`; трея нет. electron-log с ротацией; «О программе».
- `npm run desktop:dev` для разработки.

### Шаг 6. Сборка установщика
- `next.config`: `output: 'standalone'` при `DESKTOP_BUILD=1`; electron-builder NSIS (`perMachine: false`, данные в `%APPDATA%` не удаляются), белый список файлов, бинарники PostgreSQL в `extraResources`. `npm run dist` → `ERP-Энерготех-Setup.exe`.
- Скрипт-проверка содержимого сборки: нет `.env`, `*.pem`, секретов.

### Шаг 7. E2E (Playwright `_electron`) на собранном приложении
- Против docker compose: первый запуск → регистрация → snapshot → данные видны; изменение в браузере видно в десктопе; запись из десктопа видна в браузере.
- Критерии §12, которые можно проверить здесь: повторный запуск < 15 с (замер), порт 3000 занят, второй экземпляр фокусирует окно, после закрытия нет `node`/`postgres` (tasklist), тихая установка → удаление → повторная установка → данные на месте. Отдельный тест initdb в каталоге с кириллицей (§13).

### Шаг 8. Оценка объёма реплики
- `scripts/estimate-replica.ts`: размер реплики на пользователя по текущей серверной БД (по сущностям), сравнение с ориентиром 500 МБ (§10).

### Шаг 9. Приёмка P3
- Проверки, smoke, E2E; документы: новый `docs/desktop.md` (установка, данные, логи, отзыв устройства), `api.md` (device, scope/snapshot/pull), `permissions.md`, `deployment.md`, `backup.md`, CHANGELOG 0.4.0; допущения — в §14.
- **Чек-лист ручной проверки** для того, чего здесь не проверить: чистая Windows 10/11, SmartScreen без подписи, антивирус, профиль с кириллицей в имени пользователя, корпоративный CA/HTTPS.

## 3. Допущения P3 (внести в §14 после «ок»)
| Вопрос | Допущение |
|---|---|
| Запись в десктопе в P3 | только онлайн через сервер; без связи — просмотр реплики, запись недоступна (офлайн-ввод — P4) |
| HTTP-адрес сервера | разрешён только для localhost (разработка, E2E); иначе HTTPS |
| Движения склада в реплике | все склады организации (остатки как на сервере) — пересмотреть по оценке объёма |
| Отзыв устройства | администратор, владелец; автоматически — при блокировке и сбросе пароля администратором |
| Каталог данных | `%APPDATA%\ERP-Energotech`; при проблемах с кириллицей в пути — `%LOCALAPPDATA%` (решение по итогам теста §13) |
| Сборка установщика | на этой Windows-машине; CI `windows-latest` — P5 |

## 4. Риски
- embedded-postgres помечен как beta: проверяем initdb/start/stop/кириллицу тестами; при проблеме — альтернатива: официальные бинарники PostgreSQL 16 из zip EDB в `extraResources` (тот же код запуска).
- Размер установщика (Electron + Next standalone + PostgreSQL) — ожидаемо 150–250 МБ.
- Чистая Windows, SmartScreen, антивирус здесь не проверяются — только чек-лист.
- Реплика без проверки FK: при ошибке сервера возможны «висячие» строки — сервер остаётся источником истины, snapshot восстанавливает реплику.
