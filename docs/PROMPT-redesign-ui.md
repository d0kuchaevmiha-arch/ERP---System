# Промпт: редизайн интерфейса Construction ERP («Энерготех»)

> Скопируйте всё ниже линии в Claude Code, запущенный в корне репозитория.
> Сделан на основе скиллов: frontend-design (авторская позиция, plan → critique → build), taste-skill (анти-дефолтная дисциплина, «Design Read»), ui-ux-pro-max (доступность, взаимодействие, плотность данных, чек-лист).

## 0. РОЛЬ И ЗАДАЧА

Ты — арт-директор и front-end инженер небольшой студии, которая делает продукты, которые невозможно спутать с чужими. Заказчик отклонил уже несколько «нейро-шаблонных» вариантов. Задача — **перепроектировать структуру и визуальный язык** интерфейса Construction ERP так, чтобы он выглядел как инструмент из мира стройки, а не как очередная SaaS-админка.

Стек менять нельзя: Next.js (App Router), React, TypeScript, Tailwind CSS, lucide-react. Бизнес-логику, API (`src/app/api/v1`), схему БД (`src/db`), авторизацию не трогать. Работающие сценарии не ломать.

## 1. КОНТЕКСТ (сначала прочитай, потом проектируй)

Прочитай: `src/components/workspace.tsx` (все экраны в одном компоненте), `src/app/globals.css`, `src/app/layout.tsx`, `src/app/login/page.tsx`, `src/lib/overview.ts`, `src/db/schema.ts`.

Текущее состояние (что считается «приевшимся»):
- сайдбар из 12 плоских пунктов + карточка «Всё под контролем» внизу;
- каждый экран = заголовок с eyebrow → ряд одинаковых KPI-плиток с иконками в цветных квадратах → панели-таблицы;
- внутри объекта 8 горизонтальных вкладок, данные одной цепочки (этап → закупка → затрата) разорваны по разным вкладкам;
- частые операции идут через модальные окна на 6–8 полей;
- декоративные «live-dot», бейджи-точки, скруглённые карточки с мягкими тенями.

Пользователи (предположение, уточни по коду, не выдумывай роли): руководитель проекта/директор, прораб на площадке (телефон), снабженец, бухгалтер/финансы. Ничего не предполагай про страну, налоги и внешние интеграции сверх того, что уже есть в коде (рубли, ИНН — уже в проекте).

## 2. DESIGN READ (обязательный первый шаг, выведи в ответе до кода)

Одной строкой заяви: тип продукта — операционная система управления стройкой; аудитория — люди, которые принимают решения по деньгам/срокам и вносят факт с площадки; настроение — **рабочий, точный, документный, «проектная документация»**; эстетическое семейство — **инженерно-чертёжная утилитарность** (не ретро-реконструкция, а современная интерпретация).

## 3. ЗАПРЕТЫ (анти-дефолтная дисциплина)

Нельзя, даже как «акцент»:
- фиолетово-синие градиенты, mesh-фоны, свечение, glassmorphism;
- три одинаковые карточки в ряд с иконкой в цветной плитке;
- Inter/Roboto + slate-900 + белая карточка со скруглением 12–16px и мягкой тенью;
- три «типовых ИИ-образа»: (1) кремовый фон + контрастная антиква + терракотовый акцент; (2) почти чёрный фон + один кислотно-зелёный/вермильон; (3) газетная вёрстка с волосяными линиями и нулевыми радиусами без причины;
- эмодзи вместо иконок, нумерация «01/02/03» там, где нет реальной последовательности;
- декоративная анимация ради анимации; пульсирующие точки «live».

Стартовая рекомендация ui-ux-pro-max для этого запроса — «Data-Dense Dashboard, промышленный серый + сигнальный оранжевый, Fira Code/Fira Sans». Это **базовая линия, которую нужно превзойти**, а не результат: возьми из неё правила плотности данных и доступности, но не палитру и не пару шрифтов как есть.

## 4. КОНЦЕПЦИЯ: «ЛИСТ ПРОЕКТНОЙ ДОКУМЕНТАЦИИ»

Интерфейс = комплект рабочих листов, которыми пользуется стройка. Это не стилизация под «синьку», а перенос **структурных приёмов** документации в UI:

1. **Основная надпись (штамп) вместо hero и KPI-ряда.** В шапке объекта — прямоугольная таблица-штамп: шифр объекта, адрес, стадия, ГИП/РП, даты, версия плана, «отклонение: срок / бюджет / снабжение». Это единственный «заголовок» страницы. Данные в штампе — реальные из `overview.ts`.
2. **Оси и привязка вместо декоративных разделителей.** Сетка страницы размечена координатными осями (А, Б, В… по горизонтали; 1, 2, 3… по вертикали) как на плане. Оси используются по-настоящему: в графике работ — это временная шкала, в списке этапов — отметки уровней/секций. Не рисуй оси там, где они ничего не кодируют.
3. **Цепочка «объект → этап → закупка → затрата» — единая дерево-таблица (WBS-лента).** Раскрытие этапа показывает вложенные заявки, материалы, затраты и документы этого этапа. Вкладки Закупки/Материалы/Расходы/Договоры внутри объекта заменяются на фильтры-представления одной ленты.
4. **План / Факт / Прогноз — единый визуальный объект «тройная шкала».** Одна горизонтальная шкала: штриховка = план, сплошная заливка = факт, пунктир-стрелка = прогноз, засечка = договорной лимит. Используется в бюджете, сроках и материалах одинаково. Никаких «трёх плиток с процентами».
5. **Пометки на полях (marginalia).** Правая колонка страницы — «Замечания и изменения»: журнал изменений с автором и временем, открытые вопросы, документы. Это воплощает принцип «прозрачность изменений».
6. **Статусы как маркировка, а не цветные точки.** Формы статусов различаются по фигуре (не только цвету): ▲ отставание, ■ перерасход, ● принято, ◇ ожидает согласования, ⊘ заблокировано. Цвет — вторичный признак (доступность).

**Сигнатурный элемент (один, всё остальное тише):** штамп-заголовок объекта + тройная шкала «план/факт/прогноз». По ним продукт должен узнаваться.

## 5. ИНФОРМАЦИОННАЯ АРХИТЕКТУРА

Замени плоские 12 пунктов навигации:

- **Верхний контекст-бар:** переключатель объекта (или «Все объекты») + командная палитра (Ctrl/Cmd+K: «объект…», «заявка…», «внести расход…»). Выбранный объект фильтрует все разделы.
- **Левая рейка (узкая, 56–64px, только иконки + подписи по hover/focus, раскрывается по клику):** 4 группы: «Сегодня», «Объекты», «Деньги», «Снабжение». Справочники (материалы, контрагенты, договоры-реестр) — под одним пунктом «Справочники».
- **Убрать** карточку «Всё под контролем» и eyebrow-строки.
- **Правая выдвижная панель деталей (drawer)** вместо модалок для просмотра/редактирования записи. Модалка допустима только для создания новой сущности; для частых операций — быстрые действия в строке.

## 6. ЭКРАНЫ (реализовать по приоритету)

**6.1 «Сегодня» (бывший дашборд)** — не витрина, а **очередь решений**:
- главный блок — лента действий, отсортированная по срочности; в каждой строке: что, где (объект/этап), почему срочно, кнопка действия прямо в строке («Согласовать», «Принять», «Открыть»);
- ниже — «Реестр объектов» в двух режимах: **Ленты** (по объекту одна строка со штампом-мини и тройной шкалой) и **Список**. Переключатель режимов запоминается на клиенте, но страница обязана работать и без сохранённого состояния;
- графики — вторичны, один компактный блок «Бюджет: план/факт/прогноз по объектам» на общей шкале.

**6.2 Объект** — штамп-заголовок, затем три режима (переключатель-сегмент, не 8 вкладок): **Состояние** (риски, отклонения, лента изменений) · **Работа** (WBS-лента с вложенными закупками/материалами) · **Деньги** (бюджет по статьям, расходы, договоры).

**6.3 График работ** — диаграмма Ганта на осях; отставание отмечается фигурой ▲ и подписью в днях, а не только красным цветом. Прогресс — заливка в полосе.

**6.4 Закупки** — переключатель **Таблица / Этапы** (колонки-статусы: Заявка → Согласована → Заказана → Принята) с переносом по кнопке действия (drag-and-drop — дополнительно, не единственный способ).

**6.5 Склад** — остатки как «мерная линейка»: шкала от нуля до неснижаемого остатка, текущий остаток отмечен на ней; критично низкие поднимаются вверх списка.

**6.6 Режим прораба (мобильный, ≤ 480px)** — отдельная компоновка одной колонкой: «Работы на сегодня», крупная кнопка «Внести выполнение» (шаги: работа → % / объём → фото → отправить), «Заявка на материал», «Проблема на объекте». Цели касания ≥ 44px, без таблиц; данные — карточки-строки с горизонтальной шкалой.

**6.7 Экран входа** — без hero-шаблона; лист-форма со штампом продукта, минимум декоративного.

## 7. ТОКЕНЫ (предложение; проверь и при необходимости замени, но с обоснованием)

Цвет (6 именованных значений; всё остальное производное):
- «Бетон» `#D8D9D2` — фон рабочей области;
- «Калька» `#F3F3EE` — поверхность листов/панелей;
- «Тушь» `#1B1F23` — основной текст и линии;
- «Геодезическая синяя» `#2F4B7C` — линии плана, ссылки, «план»;
- «Разметка» `#E5461C` — единственный сигнальный акцент (действие, тревога), использовать экономно;
- «Арматура» `#5F6F63` — вторичный текст, «факт принят».

Семантические статусы (успех/предупреждение/ошибка) вынеси в отдельные токены и **всегда** дублируй фигурой и подписью. Проверь контраст текста ≥ 4.5:1 на каждой поверхности.

Типографика (проверь поддержку кириллицы у каждого гарнитура до внедрения): характерный акцидентный шрифт — **только** для шифров, заголовков листов и штампа (например, из семейств Geologica / Unbounded / Oswald — выбери и обоснуй один); текст интерфейса — IBM Plex Sans; числа и шифры — IBM Plex Mono / JetBrains Mono с табличными цифрами (`font-variant-numeric: tabular-nums`). Числа в деньгах выравнивай по разряду вправо.

Форма: базовый радиус 2px, у крупных панелей 0; линии 1px «тушь» с разной прозрачностью, более толстая линия (2px) только для рамки штампа. Тени не использовать; глубина — линиями и сдвигом поверхностей. Плотность: по умолчанию «компактная» (строка таблицы 32–36px) с переключателем «Комфортно» (44px).

Сетка: 12 колонок, модуль 8px; максимальная ширина контента 1440px; правая колонка «на полях» 320px, скрывается ниже 1280px в drawer.

## 8. ДВИЖЕНИЕ

Только то, что несёт смысл: раскрытие ветки WBS (высота, 160мс), выезд drawer (200мс, transform/opacity), обновление шкалы после внесения факта. Никаких параллаксов и «пульсаций». Обязательно `prefers-reduced-motion: reduce` — всё мгновенно.

## 9. ТЕКСТЫ ИНТЕРФЕЙСА

Русский, глаголы действия, sentence case: «Согласовать заявку», «Внести выполнение», не «Отправить». Одно название на действие во всём потоке (кнопка «Принять» → уведомление «Принято»). Пустые состояния — с действием («Нет заявок на этом этапе. Создать заявку»). Ошибки — что произошло и как исправить, без извинений. Используй реальные данные из seed/БД, не «Lorem ipsum» и не выдуманные цифры.

## 10. ДОСТУПНОСТЬ И ВЗАИМОДЕЙСТВИЕ (критично, приоритет выше стиля)

Видимый фокус клавиатуры везде; полная навигация с клавиатуры (палитра, рейка, WBS-дерево со стрелками, drawer закрывается Esc); `cursor-pointer` на кликабельном; hover без сдвига макета; состояние загрузки/пусто/ошибка для каждого блока; таблицы на мобильных — карточки или контролируемый горизонтальный скролл; массовые действия (чекбоксы + панель действий) в закупках и расходах; иконки только SVG (lucide) единого размера; цвет — никогда единственный носитель смысла; проверка на 375 / 768 / 1024 / 1440 px без горизонтального скролла страницы.

## 11. ПРАВА, ДАННЫЕ И БЕЗОПАСНОСТЬ (не ломать)

Не показывать в UI действия, недоступные роли пользователя; серверная проверка ввода остаётся в API как есть; никаких секретов в клиентском коде и логах; не менять `.env`. Не добавлять новые внешние сервисы и зависимости без обоснования (шрифты — через `next/font`).

## 12. ПРОЦЕСС РАБОТЫ (строго по порядку)

1. **Разведка:** прочитай файлы из раздела 1, кратко опиши текущую структуру компонентов.
2. **План дизайна (до кода):** выведи компактный дизайн-план: токены (цвет/тип/форма), карту навигации, ASCII-вайрфреймы для «Сегодня», «Объект», «Прораб (мобильный)».
3. **Самокритика плана:** для каждого решения ответь — «сделал бы я так для любого другого ERP?». Что да — перепроектируй и напиши, что изменил и почему. Убедись, что план не сползает в один из трёх запрещённых образов (раздел 3).
4. **Рефакторинг перед стилем:** раздели `workspace.tsx` на компоненты по разделам (`Shell`, `TodayView`, `ProjectView`, `PlanView`, `ProcurementView`, `WarehouseView`, `Stamp`, `TripleScale`, `Drawer`, `CommandPalette` и т.д.), без изменения поведения. Убедись, что приложение собирается и сценарии работают.
5. **Токены:** внеси токены в Tailwind-конфиг/CSS-переменные, замени стили постепенно, не переписывая `globals.css` целиком одним куском.
6. **Экраны по приоритету:** оболочка → «Сегодня» → «Объект» → остальные → режим прораба → вход.
7. **Проверка:** `lint`, `typecheck`, сборка; скриншоты каждого экрана на 375 / 768 / 1440; проверка клавиатурной навигации и контраста; сверка с чек-листом раздела 10. Сообщи, что проверено, а что нет.
8. **Финальная критика:** убери одну лишнюю деталь («сними один аксессуар»), убедись, что сигнатурный элемент — единственный яркий акцент.

## 13. КРИТЕРИИ ПРИЁМКИ

- Ни один экран не построен по шаблону «заголовок → ряд одинаковых плиток → таблица».
- Есть штамп объекта и «тройная шкала» план/факт/прогноз, и они используются единообразно.
- Цепочка «объект → этап → закупка → затрата» просматривается в одном месте.
- Частые операции выполняются без модалок (быстрые действия/drawer).
- Работает мобильный режим прораба на 375px.
- Нет регрессий: логин, создание записей, приёмка на склад, внесение выполнения — как раньше.
- Доступность из раздела 10 подтверждена проверкой; при непроверенных пунктах они явно перечислены.

## 14. ФОРМАТ ОТВЕТА
