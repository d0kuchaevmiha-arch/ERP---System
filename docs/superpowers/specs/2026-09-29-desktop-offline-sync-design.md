# ERP «Энерготех»: десктоп-клиент с офлайн-вводом и центральным сервером — архитектура

- **Статус:** дизайн согласован в обсуждении (вариант B + офлайн-ввод с синхронизацией, политика офлайн-операций — «как предложено»). Реализация не начата.
- **Дата:** 2026-09-29
- **Стек (не меняется):** Next.js 16 (App Router), React 19, TypeScript, PostgreSQL 16, Drizzle ORM, Zod, Tailwind. Десктоп: Electron + electron-builder (NSIS).
- **Обозначения:** «Проверено» — подтверждено чтением кода; «Допущение» — требует подтверждения заказчиком.

---

## 1. Цели и не-цели

### Цели
1. Одна организация (>100 пользователей) работает с **одним центральным сервером** и одной БД; у каждого — свой логин, права по роли и доступу к объектам.
2. Изменения одного пользователя видны остальным онлайн-пользователям за ≤ 5 с без ручного обновления.
3. **Полноценный ввод без связи** на ноутбуке (стройплощадка) с последующей синхронизацией; бизнес-правила (остатки, согласование, «не больше заказа») решает сервер.
4. Десктоп-приложение для Windows 10/11: `ERP-Энерготех-Setup.exe` → ярлык → окно. Без Docker/Node/Postgres у пользователя.
5. Браузерный доступ к серверу продолжает работать (только онлайн). Текущий `docker compose up` для разработки не ломается.

### Не-цели (этой итерации)
- Несколько независимых организаций (холдинг) на одном сервере — отдельный этап.
- Синхронизация файлов/фото, мобильное приложение.
- Шифрование локальной БД на уровне СУБД (закрываем BitLocker — допущение).
- Регламентированный бухучёт и интеграции (не заявлены).

## 2. Ключевые решения (кратко, с альтернативами)

| # | Решение | Выбрано | Отклонено и почему |
|---|---|---|---|
| D1 | Топология | Центральный сервер + десктоп-клиент с **локальной репликой** своих объектов + браузер (онлайн) | Только локальная БД (нет совместной работы); тонкий клиент без реплики (нет офлайна) |
| D2 | Способ синхронизации | **Очередь команд (outbox) + журнал изменений (change_log)**. Клиент отправляет *команды*, сервер прогоняет их через те же доменные проверки | Готовые движки (PowerSync/ElectricSQL — отдельный сервис, лицензии/self-host не проверены, запись всё равно через свой слой); CRDT (не держит инварианты склада/денег); репликация Postgres (двусторонние конфликты, частичные подмножества) |
| D3 | Локальная БД клиента | **embedded-postgres, мажор 16 закреплён** — тот же диалект, одни миграции Drizzle | PGlite (менее зрелый, а в outbox лежат единственные копии данных); SQLite (вторая схема и запросы) |
| D4 | UI на клиенте | Тот же Next.js standalone, запущенный локально в режиме `ERP_MODE=client`, работает с локальной БД | Переписывать UI в SPA с IndexedDB — большой рефакторинг |
| D5 | Доставка изменений онлайн | Postgres `LISTEN/NOTIFY` → **SSE** «номер журнала вырос» → клиент делает pull. Резерв — опрос раз в 30 с | WebSocket (не поддерживается route handlers Next, нужен кастомный сервер) |
| D6 | Конфликты | Решает сервер по правилам команды; спорное — в очередь «Требует решения» людям. Данные не теряются никогда | Last-write-wins для всего (теряет факты) |
| D7 | Аутентификация клиента | Онлайн-вход → **токен устройства** (отзываемый); офлайн-вход — локальный scrypt-верификатор, окно 7 дней (допущение) | Только cookie (не работает офлайн) |
| D8 | Обновления клиента | electron-updater, generic provider — **файлы обновлений раздаёт сам сервер организации** (`/updates`) | Внешний хостинг (не нужен при своём VPN) |

## 3. Компоненты

```
┌──────────────────────── Сервер организации (за VPN/прокси) ────────────────────────┐
│ reverse proxy (Caddy или nginx): HTTPS, HTTP/2, без буферизации SSE, /updates      │
│ app (Next.js standalone, ERP_MODE=server, 1–2 экземпляра)                          │
│   ├─ UI + /api/v1/*        (браузер, онлайн)                                       │
│   ├─ /api/auth, /api/auth/device                                                   │
│   ├─ /api/sync/push | pull | snapshot | events(SSE)                                │
│   ├─ domain/commands/*     ← единая точка записи (HTTP и sync)                     │
│   └─ change-listener       (1 LISTEN-соединение на экземпляр → SSE-подписчики)     │
│ db (PostgreSQL 16)  +  backup (pg_dump по расписанию, ротация, копия вне сервера)  │
└────────────────────────────────────────────────────────────────────────────────────┘
                    ▲ push (команды)      ▼ pull/snapshot (строки), SSE (сигналы)
┌──────────────────────── Ноутбук: Electron-приложение ─────────────────────────────┐
│ main: single-instance, выбор порта, запуск/остановка процессов, трей(нет), логи   │
│ ├─ embedded-postgres 16 (127.0.0.1:<свободный порт>) — реплика + outbox           │
│ ├─ Next.js standalone (ERP_MODE=client, 127.0.0.1:<свободный порт>) — UI          │
│ └─ sync-agent (отдельный Node-процесс через ELECTRON_RUN_AS_NODE)                 │
│ BrowserWindow: contextIsolation, sandbox, без nodeIntegration                     │
│ %APPDATA%\ERP-Energotech\ { pgdata, backups, logs, config.json, secrets.bin }     │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Режимы одного кода
`ERP_MODE=server` (по умолчанию, в т.ч. docker-compose) и `ERP_MODE=client` (только внутри Electron).

| Функция | server | client |
|---|---|---|
| Запись | `domain/commands` → БД сервера → change_log → NOTIFY | офлайн-разрешённые команды: локальная предпроверка → запись в локальную БД с пометкой `pending` + outbox; `online_only`-команды — синхронно на сервер через sync-agent, при отсутствии связи кнопка недоступна («нужна связь») |
| Чтение | с фильтром организации и доступа | локальная реплика (уже отфильтрована сервером) |
| Вход | cookie-сессия | локальный вход (см. §7) |
| Админ-функции (пользователи, доступы) | да | только онлайн (проксируются) |

## 4. Модель данных — изменения

Все изменения — версионными миграциями Drizzle (`drizzle/`), `drizzle-kit push` больше не используется. Для существующих БД, созданных через `push`, базовая миграция `0000` помечается применённой (baseline), данные не трогаются.

### 4.1 Сервер и клиент (общая схема)
| Таблица/поле | Назначение |
|---|---|
| `users.is_active`, `users.session_version`, `users.must_change_password`, `users.password_changed_at` | Блокировка, мгновенный отзыв сессий, смена пароля |
| `version int not null default 1`, `updated_at` на изменяемых таблицах (projects, tasks, purchases, approvals, materials, warehouses, counterparties, contracts, budget_lines) | Оптимистическая блокировка, 409 при несовпадении |
| Поля происхождения на фактах (expenses, stock_movements, purchases, task_progress_log): `origin ('online'\|'offline')`, `device_id`, `device_created_at`, `server_received_at`, `op_id` | Прозрачность: кто, где, когда ввёл, когда сервер принял |
| `task_progress_log` (task_id, progress, actual_quantity, author, device_created_at, …) | История фактов выполнения; `tasks.progress` = последнее по `device_created_at` |
| `purchases.number` присваивает сервер; `purchases.local_ref` — временный номер клиента | Нумерация без коллизий офлайн |

### 4.2 Только сервер
| Таблица | Поля (основные) |
|---|---|
| `devices` | id, user_id, name, app_version, token_hash, registered_at, last_sync_at, revoked_at |
| `change_log` | seq bigserial PK, organization_id, project_id null, entity, entity_id, op ('upsert'\|'delete'), changed_at. Пишется **в той же транзакции**, что и данные (из доменного слоя). Хранение 90 дней (допущение) |
| `sync_ops` | op_id uuid PK, device_id, user_id, command, status ('applied'\|'rejected'\|'conflict'), result jsonb, device_created_at, received_at — идемпотентность |
| `sync_conflicts` | id, op_id, organization_id, project_id, kind, payload jsonb, reason, status ('open'\|'resolved'\|'discarded'), assigned_role, resolved_by, resolved_at, resolution jsonb |
| `login_attempts` | ключ (email+ip), count, until — замена счётчика в памяти |
| `audit_logs` | + `origin`, `device_id`, `device_created_at`. **Не реплицируется** на клиенты |

### 4.3 Только клиент
| Таблица | Поля |
|---|---|
| `outbox` | op_id, command, payload jsonb, device_created_at, status ('pending'\|'sending'\|'applied'\|'rejected'\|'conflict'), error, attempts, depends_on op_id[] |
| `local_rows` | op_id → (entity, entity_id): какие оптимистичные строки создала операция (для отката при отказе) |
| `sync_state` | server_url, device_id, last_seq, last_pull_at, last_push_at, protocol_version, offline_scope (project ids) |

## 5. Доменный слой и команды (сервер — единственный источник истины)

Сейчас вся запись — в одном `src/app/api/v1/[resource]/route.ts` (~18 КБ). Выносим в `src/server/domain/commands/<name>.ts`:

```ts
type Command<I> = {
  name: string;                       // 'movements.issue', 'progress.set', ...
  schema: z.ZodType<I>;               // серверная валидация
  offline: 'allowed' | 'conflictable' | 'online_only';
  authorize(user, input, tx): Promise<void>;       // роль + project_access ВСЕГДА (в т.ч. по taskId/purchaseId)
  execute(tx, user, input, ctx): Promise<Result>;  // бизнес-правила, запись, audit, change_log
  onConflict?(err, input): ConflictSpec;           // для 'conflictable'
};
```
- HTTP `POST /api/v1/<resource>` и `POST /api/sync/push` вызывают **один и тот же** реестр команд. HTTP принимает необязательный заголовок `Idempotency-Key` (= op_id).
- В конце транзакции — `pg_notify('erp_changes', json{org, projectIds, maxSeq})` (доставляется только после commit).

### 5.1 Политика офлайн-операций (согласована)
| Команда | offline | Правило при приёме сервером |
|---|---|---|
| `progress.set` | allowed | Пишется в `task_progress_log`; в `tasks` применяется, если `device_created_at` новее текущего, иначе остаётся в истории |
| `expenses.create`, журнал/заметки | allowed | Принимается (только добавление) |
| `purchases.create` | allowed | Статус `requested`, номер присваивает сервер |
| `movements.receipt`, `movements.return` | allowed | Принимается |
| `movements.issue`, `movements.writeoff` | conflictable | advisory lock (как сейчас); остатка не хватает → конфликт `insufficient_stock`, решает кладовщик/РП |
| `purchases.receive` | conflictable | `SELECT … FOR UPDATE` заявки; превышение заказа → конфликт `over_receipt`, решает РП/снабжение |
| `approvals.decide` | online_only | `UPDATE … WHERE status='pending' RETURNING`; 0 строк → «уже решено ‹кем›» |
| budgets, contracts, projects.create, materials/warehouses/counterparties, users, access | online_only | Обычная онлайн-запись |

Общие правила приёма: нет доступа к объекту → `rejected: no_access`; пользователь заблокирован раньше `device_created_at` → `rejected: user_blocked`; операция зависит от отклонённой → `rejected: dependency_rejected`.

### 5.2 Исправления текущего кода (обязательны до сети; проверено чтением)
1. `getOverview()` читает все строки без фильтра организации и доступа → фильтр по `organizationId` и доступным объектам (director/super_admin — все объекты своей организации); список пользователей — только своей организации.
2. `ERP_PRIVATE_MODE` по умолчанию `true`; в `ERP_MODE=server` без входа — никаких данных.
3. Проверка `project_access` выполняется только при наличии `projectId` → переносится в `authorize` каждой команды (progress по taskId, approvals/receive по purchaseId, movements по складу/проекту).
4. Гонки: approvals (условный UPDATE), receive (FOR UPDATE), progress (история + version).
5. `actualQuantity || old` не позволяет записать 0 → `??`.
6. `SESSION_SECRET` без фолбэка на `DEMO_PASSWORD`; сессия проверяет `is_active` и `session_version`.
7. Rate limit входа — в `login_attempts`; `X-Forwarded-For` доверять только от прокси (`TRUSTED_PROXY`).

## 6. Протокол синхронизации (v1)

Все эндпоинты: HTTPS, `Authorization: Bearer <device token>`, заголовок `X-Sync-Protocol: 1`. Несовместимая версия → `426` + требование обновить клиент (outbox сохраняется).

### 6.1 Регистрация устройства
`POST /api/auth/device` {email, password, deviceName, appVersion} → {deviceId, token, user, offlineScopeDefault}. Токен хранится на клиенте через `safeStorage` (DPAPI), на сервере — только хеш. Отзыв: `devices.revoked_at` или блокировка пользователя → `401` на любой sync-запрос.

### 6.2 Начальная загрузка
`GET /api/sync/snapshot?entity=<name>&projects=<ids>&cursor=<c>` → {rows, nextCursor, snapshotSeq}. Клиент грузит по сущностям страницами, затем начинает pull с `snapshotSeq`. Также используется при добавлении объекта в офлайн-набор и если `last_seq` старше срока хранения change_log.

### 6.3 Получение изменений
`GET /api/sync/pull?since=<seq>&limit=1000` → {changes:[{seq, entity, id, op, row|null}], nextSeq, hasMore}. Сервер отдаёт **текущую** версию строки (дедуп по id), только в пределах организации и `offline_scope` ∩ доступ пользователя. Справочники (materials, counterparties, warehouses) — всей организации. Доступ отозван → `op:'delete'` для всех строк объекта.

### 6.4 Отправка команд
`POST /api/sync/push` {deviceId, ops:[{opId, command, payload, deviceCreatedAt, dependsOn[]}]} (≤ 200 за раз, порядок сохраняется) → {results:[{opId, status, entityIds?, error?, conflictId?}]}. Каждая операция — своя транзакция; повтор `opId` возвращает сохранённый результат из `sync_ops`.

### 6.5 Сигналы
`GET /api/sync/events` (SSE; device token или cookie) → `event: changes data:{maxSeq}` по объектам пользователя; heartbeat каждые 25 с. Браузерный UI подписывается тем же каналом и вызывает `refresh()` с задержкой 1–2 с (debounce).

### 6.6 Цикл sync-agent на клиенте
1. Есть связь? → push всех `pending` по порядку → обработать результаты: `applied` — пометить; `rejected` — откатить строки из `local_rows`, запись остаётся видна в «Не принято сервером» с причиной; `conflict` — строки помечены «спорно», видны в «Требует решения».
2. pull до `hasMore=false` → upsert в реплику (серверная строка заменяет оптимистичную с тем же id).
3. Ждать SSE-сигнал или 30 с; при ошибках — экспоненциальная пауза до 5 мин.
4. Индикатор в шапке: «Онлайн · синхронизировано 12:04», «Офлайн · 7 изменений в очереди», «Есть отклонённые (2)».

## 7. Безопасность

- Сервер: только HTTPS (и внутри VPN), HTTP/2; порт БД наружу закрыт; отдельный пользователь БД без суперправ; секреты в `.env` на сервере/Docker secrets, не в репозитории и не в образе.
- Клиент: Postgres и Next слушают **только 127.0.0.1**, пароль локальной БД и секреты генерируются при первом запуске, хранятся через `safeStorage` в `secrets.bin`; `.env` в сборку не попадает (белый список файлов electron-builder).
- Electron: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `setWindowOpenHandler` → внешние http(s) в системном браузере, `will-navigate` на чужие адреса блокируется, проверка TLS-сертификата сервера **не отключается** (корпоративный CA ставится в систему — допущение).
- Офлайн-вход: после онлайн-входа сохраняется scrypt-верификатор пароля (DPAPI). Офлайн-вход разрешён ≤ 7 дней с последней успешной онлайн-аутентификации (допущение), затем — только онлайн. Смена пароля/блокировка применяются при ближайшей синхронизации.
- Кража ноутбука: локальная БД содержит данные объектов → требование BitLocker на ноутбуках (допущение, зона ИТ); админ может отозвать устройство.
- Аудит: каждая принятая офлайн-операция записывается с `origin=offline`, `device_id`, обоими временами.

## 8. Десктоп-оболочка (из первого плана, без изменений по сути)

- `app.requestSingleInstanceLock()`: второй запуск фокусирует окно.
- Свободные порты через `net.listen(0)`; сервер Next — `ELECTRON_RUN_AS_NODE` + `.next/standalone/server.js`, `HOSTNAME=127.0.0.1`.
- Экран загрузки опрашивает `/api/health`; первый запуск: initdb → миграции → экран «адрес сервера + вход» → snapshot с прогрессом.
- Закрытие окна = выход: остановка sync-agent → Next → Postgres (`pg_ctl stop -m fast`), при сбое — `taskkill /T /F`. Трея нет (иначе процессы остаются после закрытия).
- Перед локальной миграцией — «холодная» копия `pgdata` в `backups\` (хранить 5). Кнопка «Экспорт очереди» сохраняет неотправленные операции в файл (на случай, если устройство отозвано).
- Устаревший `postmaster.pid` после сбоя: проверить, что процесс не жив, удалить.
- Логи: electron-log + stdout Next/Postgres/sync-agent → `logs\`, ротация.
- «О программе»: версия приложения, версия протокола, сервер, последняя синхронизация.
- `next.config.ts`: `output: 'standalone'` только при `DESKTOP_BUILD=1` (или везде, если Dockerfile переведён на standalone — решить в P5).
- Сборка: `npm run dist` → electron-builder NSIS, `perMachine: false`, данные в `%APPDATA%` не удаляются при удалении программы. Собирать на Windows или в CI `windows-latest`.

## 9. Серверное развёртывание

- `docker-compose.prod.yml` (новый; текущий `docker-compose.yml` остаётся для разработки): proxy + app + db + backup.
- Контейнер app при старте: `node dist/migrate.js` (версионные миграции, перед ними `pg_dump`), затем `node server.js`. Seed — только отдельной командой, не при старте.
- Бэкапы: ежедневный `pg_dump -Fc`, хранение 14 дневных + 8 недельных (допущение), копия вне сервера; ежемесячная проверка восстановления на тестовой БД (runbook).
- Нагрузка (допущение): 100–500 пользователей, до ~100 одновременно — один сервер PG, 1–2 экземпляра app. Узкое место — тяжёлый overview; при росте — лёгкие эндпоинты и пагинация.
- Раздача обновлений клиента: `/updates/latest.yml` + установщик на том же прокси.

## 10. Объём данных на ноутбуке (неизвестен → измеряем)

- Реплицируются только объекты из `offline_scope` (по умолчанию — объекты, где у пользователя есть доступ; пользователь может снять/добавить объект в «Доступно офлайн»), справочники организации, свои уведомления. `audit_logs` не реплицируется.
- Для ролей со всеми объектами (директор) по умолчанию офлайн-набор пуст → выбирает вручную.
- В P3 — скрипт `scripts/estimate-replica.ts`: размер реплики на пользователя по текущей БД. Целевой ориентир ≤ 500 МБ (допущение). Если больше — окно истории (например, движения старше 12 мес — только онлайн).

## 11. Тестирование и критерии приёмки

- Unit: каждая команда (валидация, authorize, бизнес-правила).
- Интеграционные на реальном PostgreSQL 16 (docker): изоляция («пользователь орг. X не видит Y», «прораб без доступа не меняет чужой объект»), гонки (2 параллельных receive/approve → ровно 1 успех), идемпотентность push.
- Сценарные sync-тесты: два эмулированных клиента против тестового сервера — офлайн-списание последних 10 ед. обоими → 1 applied + 1 conflict; отклонённая операция откатывается локально и видна с причиной; отзыв доступа удаляет объект с клиента.
- E2E (Playwright `_electron`): установка → запуск < 15 с (повторный), вход, офлайн-ввод, восстановление связи, синхронизация.
- Всегда: `npm run typecheck`, `npm run lint`, `npm run build`, `scripts/smoke.ts`.

## 13. Риски

| Риск | Смягчение |
|---|---|
| Сложность P4 (конфликты, откаты) | Сценарные тесты до кода; ограниченный набор офлайн-команд (§5.1) |
| Postgres на Windows: права администратора, кириллица в пути профиля, антивирус | Проверить в P3 на чистой ВМ; initdb с `UTF8`/`C`; при проблеме с путём — короткий путь данных (вариант: `%LOCALAPPDATA%`) |
| Объём реплики у ролей с большим доступом | Офлайн-набор объектов выбирается; оценка в P3; окно истории |
| Расхождение версий клиента и сервера | Версия протокола, 426, обновление с сервера, outbox переживает обновление |
| Неверные часы на ноутбуке | Храним `device_created_at` и `server_received_at`; порядок фактов — по устройству, проверки — по серверу |
| Утечка данных до P1 | Не выставлять сервер в сеть до завершения P1 |
| SmartScreen/антивирус без подписи установщика | Сертификат подписи кода — решение заказчика |

## 14. Допущения и открытые вопросы

| Вопрос | Допущение по умолчанию |
|---|---|
| Число пользователей | 100–500 всего, до ~100 одновременно |
| Объём данных на ноутбук | Неизвестен; измеряем в P3, ориентир ≤ 500 МБ |
| Офлайн-вход без связи | ≤ 7 дней |
| Шифрование дисков | BitLocker на ноутбуках (ИТ) |
| Кто разбирает конфликты | склад — кладовщик/РП объекта; приёмка — РП/снабжение |
| Формат номера заявки | серверный сквозной номер организации; офлайн — временный `local_ref` |
| Хранение change_log | 90 дней |
| Сертификат HTTPS | корпоративный CA или публичный — установлен в систему клиентов |
| Название в интерфейсе десктопа | «Энерготех» (через `NEXT_PUBLIC_BRAND_*` при сборке) |
| Подпись установщика | пока без подписи |
| Кто управляет пользователями и доступами (P1) | `super_admin` и `director` своей организации; назначать/изменять `super_admin` — только `super_admin`; себя заблокировать или сменить себе роль нельзя |
| Политика пароля (P1) | ≥ 10 символов; временный пароль — 16 случайных символов, обязательная смена при входе |
| Видимость справочников (P1) | materials, counterparties, warehouses — вся организация; остатки считаются по всем складам организации |
| Движения и договоры без объекта (P1) | движения общих складов видны всей организации; договоры без объекта — director, super_admin, finance_manager, accountant |
| Журнал аудита в UI (P1) | director/super_admin — вся организация; остальные — только свои действия |
| Реальный IP клиента (P1) | Route handler Next не видит адрес сокета: при `TRUSTED_PROXY=1` — крайний правый `X-Forwarded-For`, иначе ключ лимита входа — только email |
| Запись в общий склад без объекта (P1) | разрешена ролям записи (как до P1): `project_access` к нему неприменим |
| Создание объекта (решено в P2, вариант A) | любая роль записи; автор, не имеющий доступа ко всем объектам организации, автоматически получает `edit` |
| Формат номера заявки (P2) | `ЗК-<год приёма сервером>-<NNNNN>`, сквозной счётчик организации (не сбрасывается по годам); старые номера не меняются |
| Хранение `sync_ops` (P2) | бессрочно до P5 (очистка — вместе с политикой бэкапов) |
| Факты до 0.3.0 (P2) | `origin='online'`, `server_received_at = created_at`, `device_created_at` неизвестно (NULL) |
| Задержка обновления в браузере (P2) | сигнал SSE — десятки мс, обновление сводки через 1,5 с (debounce); без SSE — до 30 с |
| Дата окончания работы (P2) | `actual_end` — дата (UTC) времени ввода на устройстве для факта 100% |
| `version` у пользователей (P2) | не вводится: у `users` своя `session_version`; `users.update` без 409 (изменения администраторов редки) |
